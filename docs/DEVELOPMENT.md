### 프로젝트 구조

Gradle 모듈 하나, 기능별 패키지로 나눈다.

```
com.companyinsight
├── company       기업 목록(고유번호), 검색
├── disclosure    공시 수집, 규칙 분류
├── analysis      작업 큐, 워커, 본문 받기, 표 읽기, AI 판정·요약, 원문 대조 검증
├── score         호재/악재 점수, 일별 추이
├── financial     재무 수집
├── backfill      Spring Batch 백필
├── ops           수집 실행 기록, 운영자 알림
├── web           화면(Thymeleaf 컨트롤러)
└── common        설정, 외부 API 공통(타임아웃·재시도·속도 제한)
```

### 추가와 수정이 쉬운 구조

미국·일본 상장사를 MVP 이후에 추가한다. 그때 구조를 뜯어고치지 않도록 다음을 지킨다.

- 회사는 내부 번호(`id`)를 기준 키로 쓰고, 나라(`country`)와 출처(`source`), 그 출처에서의 번호(`source_key`. DART는 고유번호)를 따로 저장한다. 다른 테이블은 회사를 내부 번호로 참조한다.
- 공시의 중복 방지는 "출처 + 그 출처의 공시 번호"(`source`, `source_key`. DART는 접수번호) unique로 한다.
- 출처와 나라의 값은 코드(enum `Source`, `Country`)가 정한다. DB에는 값 목록을 CHECK로 두지 않아, 출처를 추가할 때 스키마를 고치지 않는다.
- 회사 검색 API와 공시 목록 화면은 회사를 내부 번호로 가리킨다. 출처의 번호는 밖으로 내보내지 않는다. 내부 번호는 DB를 새로 만들면 달라지므로, 오래 남는 공개 주소(종목 화면)에 쓸 회사 식별자는 종목 화면을 만드는 단계에서 정한다.
- 수집기와 제목 규칙은 출처별로 나눠, 새 출처를 추가할 때 기존 코드를 고치지 않게 한다.
- 새로 만드는 테이블(재무, 분석, 판단)은 회사의 내부 번호를 참조하고, 금액에는 통화를 함께 저장한다(재무는 응답 안에 줄마다 통화가 들어 있다).
- 재무는 출처가 준 응답을 보고서 한 건 단위로 그대로 저장한다(`financial`). 화면에 쓰는 계정(매출액, 영업이익, 당기순이익)과 4분기 금액(연간 − 3분기 누적), 전년 동기 대비 증감, 영업이익률은 조회할 때 저장된 응답에서 읽어 계산한다. 계정을 추가하거나 읽는 규칙, 계산 방식을 고쳐도 다시 수집하지 않는다. 계정이 하나도 없는 응답과, 읽을 수 있는 계정이 없는데 이미 저장된 응답에서는 읽을 수 있는 경우는 저장하지 않아 쓸 수 있는 응답을 덮어쓰지 않는다. 보고서에 연결재무제표가 있으면 연결을, 없으면 별도를 쓴다. 반기·3분기보고서의 금액이 3개월 금액이라고 볼 근거(누적 금액이 따로 있음)가 없으면 그 분기는 내보내지 않는다.
- 수집 기능은 회사 한 곳을 지정해 받을 수 있게 만든다. 기능을 완성한 뒤 테스트 회사 몇 곳으로 확인하고, 이상이 없으면 전 종목 데이터를 채운다.

### 주요 테이블 (초안)

| 테이블 | 핵심 컬럼 |
|---|---|
| `company` | id(PK), country, source, source_key(source와 묶어 **unique**. DART는 고유번호), stock_code, name, market |
| `disclosure` | id, source, source_key(source와 묶어 **unique**. DART는 접수번호), company_id, report_name, rcept_date, type_code, title_rule_id, title_rule_version, case_code, normalized_title, title_attributes, tone, impact, impact_ratio(크기를 정할 때 본 원래 비율), classified_by(RULE 제목 규칙/TABLE 본문 표/LLM), is_correction, is_withdrawn |
| `disclosure_type` | code(PK. 예: A1), bundle, name, judge_method(TITLE/CODE/AI), default_tone, fetch_body, sort_order |
| `title_rule` | id, source, match_kind(EXACT/FORM/FORM_WORD), pattern, tail_word(FORM_WORD 줄의 꼬리 낱말. source, match_kind, pattern과 묶어 **unique**), type_code, tone, judge_method, case_code, memo, added_version |
| `title_attribute` | source, token(제목에서 떼는 속성 꼬리), attribute |
| `title_rule_version` | version(PK), applied_at, note. 대응표를 고치는 마이그레이션마다 한 줄 |
| `disclosure_summary` | disclosure_id, lines(핵심 3줄), model, verified |
| `analysis_job` | id, disclosure_id, stage(FETCH_BODY/READ_TABLE/AI_JUDGE/AI_SUMMARY. disclosure_id와 묶어 **unique**), status(PENDING/RUNNING/DONE/FAILED), outcome(ENDED/PASSED/NO_BODY/HELD), priority, run_after, attempts, deferrals, enqueue_reason, locked_at, last_run_id. 공시 한 건의 한 단계가 한 행 |
| `analysis_run` | job_id, disclosure_id, stage, started_at, finished_at, outcome, enqueue_reason, pass_reason, error_kind, error_code, error, result(JSONB), setting_version_id, input_tokens, output_tokens. 실행 한 번이 한 행이고 쌓기만 한다 |
| `disclosure_body` | disclosure_id(PK), content(출처가 준 본문 압축 파일 그대로, bytea), byte_size, file_count, fetched_at. 공시 한 건의 본문 원문이 한 행. 글자는 저장하지 않고 쓸 때마다 뽑는다 |
| `company_score` | company_id, date, score, up_sum, down_sum (company_id+date unique) |
| `financial` | company_id, source, fiscal_year, report_type(Q1/HALF/Q3/ANNUAL. 넷을 묶어 **unique**), payload(출처 응답 전체, JSONB), fetched_at. 보고서 한 건의 응답 하나가 한 행 |
| `collection_run` | source, started_at, finished_at, status, fetched, saved, error, error_kind, error_code |

`company`, `disclosure`, `disclosure_type`, `title_rule`, `title_attribute`, `title_rule_version`, `collection_run`, `financial`, `analysis_job`, `analysis_run`, `disclosure_body`는 만들어져 있다. 나머지 테이블의 컬럼은 해당 단계에서 확정한다.

### 브랜치 전략 (GitHub Flow)

- `main`은 항상 배포 가능한 상태다. 직접 push할 수 없고, PR로만 합친다.
- 작업은 `main`에서 브랜치를 만들어 하고, 3절의 단계 하나를 브랜치 하나·PR 하나로 한다.
- 브랜치 이름은 커밋 접두어와 같다.

| 접두어 | 용도 | 예 |
|---|---|---|
| `feat/` | 기능 | `feat/disclosure-polling` |
| `fix/` | 버그 수정 | `fix/duplicate-rcept-no` |
| `chore/` | 설정, 빌드, 배포 | `chore/deploy-pipeline` |
| `docs/` | 문서 | `docs/readme-architecture` |
| `test/` | 테스트 | `test/job-queue-concurrency` |

- 커밋 메시지도 같은 접두어(`feat:`, `fix:`, `chore:`, `docs:`, `test:`)로 시작한다.
- PR은 CI(`build`)가 통과하고 브랜치가 최신 `main`을 반영해야 합칠 수 있다.
- 합칠 때는 Squash merge만 쓴다. 합친 브랜치는 자동 삭제된다.
- 공개 오픈 시점에 `v0.1.0` 태그를 붙이고, 이후 큰 기능마다 버전을 올린다.

| 단계 | 담당 |

- 비밀 값은 `.env`에만 둔다.

### 코드 리뷰

코드를 작성한 에이전트는 자기 코드의 문제를 잘 보지 못한다. 그래서 리뷰는 작성 과정을 모르는 별도 에이전트가 한다.

1. 코드를 바꾸는 PR은 **Draft**로 만든다. Draft는 Merge할 수 없으므로 리뷰 도중에 합쳐지지 않는다.
2. PR을 만든 직후 별도 리뷰 에이전트에게 검토를 맡긴다. 리뷰 에이전트는 작성 과정을 모르는 상태에서 diff와 저장소 규칙(`CLAUDE.md`, `docs/CONVENTIONS.md`)만 보고 검토하며, 파일을 고치지 않고 보고만 한다.
3. 보는 것: 동작 오류, 누락된 예외·경계 처리, 동시성, 보안(비밀 값 노출, 입력 검증), 규칙 위반, 빠진 테스트.
4. 확인된 문제는 같은 브랜치에서 고쳐 push하고, 로컬 빌드와 CI를 다시 통과시킨다.
5. 리뷰 결과(지적 사항, 고친 것, 고치지 않은 것과 이유)를 PR 댓글로 남긴다.
6. 리뷰 반영을 push한 뒤 PR을 Ready for review로 바꾼다. 이때부터 Merge할 수 있다.
7. 문서만 바꾼 PR은 리뷰를 생략하고 바로 Ready로 만들 수 있다.

### PR 완료 기준

1. 새 로직에 테스트가 있다. 점수 계산, 규칙 분류, 원문 대조 검증은 단위 테스트, DB 쿼리와 작업 큐는 Testcontainers 테스트.
2. CI가 통과한다.
3. 독립 코드 리뷰를 거쳤고, 확인된 문제를 고쳤다.
4. 결정이 바뀌었으면 `PLAN.md` 또는 이 문서를 함께 고쳤다.

## 3. 기능 개발 순서

### 순서를 정한 원칙

1. **종목 화면까지의 흐름을 먼저 완성한다.** 이 서비스가 보여주는 것은 공시 목록이 아니라 회사 한 곳에 대한 판단과 근거다. 재무 수집, 본문 분석, 판단 계산, 종목 화면을 먼저 잇고, 배포와 공개 오픈은 그 뒤에 한다.
2. **구조 변경이 새 테이블보다 먼저다.** 재무·분석·판단 테이블이 모두 회사를 참조하므로, 회사와 공시의 기준 키를 바꾸는 일은 테이블이 늘기 전에 한다.
3. **기능이 데이터보다 먼저다.** 데이터가 많이 쌓인 뒤에는 구조를 고치기 어렵다. 기능을 완성하고 테스트 회사 몇 곳의 실제 데이터로 확인한 뒤 전 종목 데이터를 채운다.
4. **규칙이 LLM보다 먼저다.** 규칙으로 처리되는 비율을 먼저 재야 LLM에 보낼 양을 알 수 있다.
5. **작업 큐가 LLM보다 먼저다.** LLM 호출은 느리고 실패하므로 재시도 구조 위에 올린다.
